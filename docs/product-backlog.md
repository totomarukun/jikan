# TacTap プロダクトバックログ (PM管理)

運営方針: 超リアルなペルソナによる外部評価サイクルを回し、
大玉から徹底的に改善する。機能の改廃も躊躇しない。

## 運営方針の改訂 (サイクル15〜: 根本改善ループへ)
サイクル11〜14で必需3→6〜7まで改善したが、独立評価が3回連続で「9点の壁は
コミュニティのデータ密度(コールドスタート)であり、設計は誠実で正しく、偽データは禁じ手」
と収束。バグ潰し型のループは頭打ちと判断し、**プロダクトの根本価値を問い直すループ**に
切り替える。問い直すべき論点 (ユーザー指示):
- **A/B強制選択そのものが価値なのか**: 作業感があり、疎なデータでは結論が出ない。
  別のコア体験(相対マップの閲覧・定性レビューの消費)の方が必需度が高い可能性。
- **マイギア中心が正しいのか**: 個人の使用履歴を軸にするのは正しいが、それが
  コア価値の置き場として最適か。
- **データから導く「全用具の相対マップ」**: 蓄積したA/B比較から、推移性を使って
  疎なデータでも全用具の相対位置(軸別)を導きダッシュボード化する。同じデータから
  より多くの価値を引き出し、コールドスタートを部分的に克服できる仮説。
- **定性レビューの深堀り**: 体感メモ/feel statements を、用具選びの意思決定に
  効く深さまで掘れる構造にする。
→ 評価プロンプトも「バグ探し」から「根本的な価値提案の妥当性と、最も必需度を上げる
  構造転換の提案」に訂正する (下記サイクル15のプロンプト参照)。

### サイクル14 対応 (独立評価サイクル13の指摘。実装で直せる分のみ対応)
独立評価5回目: **必需6 / 手軽7 / 手間7**(手間5→7)。評価者の結論=「9点の壁の本質は
①コミュニティのデータ密度の問題(設計は誠実で正しく、偽データ投入は禁じ手)。②③は実装で直せる」。
- **② 最初の質問が現用と無関係なイメージ質問**: ギア未登録で /play に来ると、いきなり
  ランダムな2本のイメージ質問が出て、両方使った人の比較を期待した第一印象を損ねていた。
  - 修正(`play/page.tsx`): gearCount===0 のときはランダム質問ではなく
    **ギア登録ゲート**を表示。「まず使ったラバーを登録(同じ面で2本以上)」を促し、
    `?explore=1` で明示的にイメージ回答も試せる導線を残す。
  - 検証(実走): ギア0本 /play でゲート表示・イメージ質問は非表示、
    /play?explore=1 でイメージ質問に進めることを確認。
- **③ /me が空(評価者の誤診)**: /me はサーバコンポーネントで本来SSRされる。評価者が
  空を見たのは匿名セッションで未ログイン→/loginリダイレクトのため(設計通り、匿名は/gear)。
  実バグではないため変更なし。
- **① コミュニティ結論が0件**: コールドスタート=実データ密度の問題。評価者自身が
  「設計は誠実で正しい」と明言。コードでは解決不可(偽データは禁じ手)。GTM/初期データ
  獲得の経営課題であり、実装サイクルの守備範囲外。次セクション「9点の壁」に整理。

### 9点の壁の構造的分析 (サイクル14時点)
- サイクル11〜14で必需3→6〜7・手軽6→7・手間4→7まで改善。器(乗り換え動線・自分の判定の
  可視化・誠実なn表示・スペック不信への配慮)は独立評価で一貫して信頼を獲得。
- 残る最大の壁=「両方使った他人の結論」が0件。これは実装ではなく**実ユーザーの蓄積**が
  必要で、偽データ投入は企画書のブランド指針・本バックログの運用ルールに反する禁じ手。
- よって必需9達成にはコード改善ではなく、初期ユーザー獲得/データ獲得施策(GTM)が要る。
  実装で残る価値はUXのポリッシュ(②のような第一印象改善)に限られる。

### サイクル15 (根本転換): 相対マップ — 3票ゲートを撤廃し疎データから結論を出す
独立評価6回目(**根本価値の問い直し**。バグ探しでなく中核設計の妥当性を問う)。
評価者の必需スコアは**1.5/10**(単独ユーザー・疎データでは意思決定材料が一切出力されない)。
- 評価者の診断: **病巣はA/B比較という手法でなく、結論を全部「ペアに3票溜まったら」に
  先送りする集計モデル**。switch空・自分の票が返らない・全出口が3票ゲートで、
  単独ユーザーは構造上永遠に結論に到達できない(=コールドスタートで死ぬ設計)。
- 評価者が選んだ最優先の構造転換=**仮説(A) 推移律ベースの全用具・軸別相対マップ**。
  同じA/B入力をペア勝率でなく1枚の順序推定に合成すれば、A&gt;B・B&gt;C ⇒ A&gt;C で
  疎データでも全体地図が描け、1票が地図全体に寄与する。マイギアは回答ノルマの起点でなく
  地図上の原点(現在地マーカー)に。到達見立て: (A)実装で必需7、(C)定性深堀り併用で8.5。
- **実装**:
  - `lib/ranking.ts`: 正則化Bradley-Terry(MM法)。全比較を1つの強さ推定に合成。
    仮想アンカー(平均ラバー)と各項目をalpha回引き分けさせ、(1)グラフ分断でも単一
    スケール (2)全勝/全敗でも有限値 (3)支持薄は中央へ縮約、を同時に満たす。
    比較ごとに信頼度重み(実体験1.0/イメージ0.4)。`__tests__/ranking.test.ts`で
    推移律(A&gt;B,B&gt;C⇒A&gt;C)・矛盾比較の互角収束・信頼度効果を検証。
  - `lib/relative-map.ts`: DBの全比較→軸別(好み/速/スピン/硬/球持ち)の相対マップ。
    ラバー同士のみ。各ラバーに実比較本数と「両方使った人」本数を付与。
  - `app/map/page.tsx` + ナビ導線: 軸タブ・相対位置バー・マイギアを原点フラグ
    (使用中/マイギア)・支持本数(実◯/全◯件)・支持<3は「中央寄りの暫定位置」と明示。
    3票ゲートを撤廃し「推定位置+信頼度」で常に何かを返す。空軸は正直な空状態+導線。
  - 検証(実走): ロゼナ&gt;テナジー05・テナジー05&gt;ラクザ7 を投入→ /map?axis=speed で
    **ロゼナ&gt;テナジー05&gt;ラクザ7**(ロゼナとラクザ7は直接対決なし=推移律が実証)。
    複数セッションの比較が同一地図に合成され、マイギアが「使用中」でフラグされることを確認。
- 次の論点: (C)定性レビュー深堀り(候補3本に絞った後の最終確認層)、推移律推定の信頼性
  (循環・矛盾の扱い、信頼区間の可視化)、/switch・compareをマップ基盤へ統合。

### サイクル16の評価反復 (独立評価7〜10回目。各指摘を実装で即対応)
再設計後、コア価値が成立したかを独立評価で連続検証し、出た実装可能な指摘を1つずつ潰した。
- **評価7 必需6.5**: 「コア価値成立・推移律を評価者が実機確認・致命傷(疎データで無)は構造的に解消」。
  最優先=/switchが直接対決依存でコールドスタート空 → **buildSwitchCandidates で相対マップ基盤化**。
- **評価8 必需5**: 定性レビュー追加を確認も、致命バグ発見=「両方ギア登録後の声が"イメージ"表示」。
  → answers API更新分岐で **hasActualExperience を毎回再判定**。加えて差分が方向のみで量が無い指摘
  → /switch に **相対位置差(0-100)** を追加。
- **評価9 必需6**: バグ修正と量を確認。最優先=「量に確信度が無く、疎データの飽和値(▼-100)が
  堅牢な推定と同じ見た目」 → /switch チップに **支持本数n併記・薄い根拠はグレー縮約・参考程度バッジ**。
- **評価10 必需6**: 確信度設計を「優秀」・定性レビュー「完全に通る」・推移律「効く」と確認。
  残る決定的要因は**構造的なデータ供給**: (a)nは人単位で単独ユーザーは閾値を越えられず量が出ない
  (=コールドスタートの正直な現実) (b)投稿口がoverall固定で軸別nが枯渇 → **体感フォームを軸別投票へ
  拡張**(好み+任意で各軸)。
- **到達点と結論**: 必需1.5→6.5→(バグ発見で5)→6。**方向・推移律・定性レビュー・経験フラグ・確信度表示は
  9点級**。残る6→9の壁は、サイクル14と同じ**実ユーザーのデータ密度(コールドスタート)**に収束。
  軸別投票UIで供給面の枯渇は塞いだが、量(数値差)の確信は複数ユーザーの蓄積を要する=GTM課題。
  偽データ投入は禁じ手。コードで残る価値は供給導線とUXのポリッシュに限られる。
