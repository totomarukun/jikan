### サイクル10 対応 (看板・ランキングの水増し耐性。実装済み・攻撃再現で検証)
- 公開集計を詐称不能な実体験(BOTH)基準に統一: aggregatePairs に
  experiencedOnly を追加し、/battles ランキング・トップ「注目の対決」・
  用具ページの対決一覧・用具の「好み勝率」をすべて BOTH のみ集計に。
  トップ看板を「累計AB比較回答(全票)」→「両方使った人の判定(BOTH数)」に変更
- 検証: 評価者と同じ攻撃(使い捨て匿名セッション8個から投票)を再現し、
  公開面のn・ランキング順位が一切動かないことを確認(ボット票はNEITHERで除外)
- 残課題(次サイクル以降): ①各使い捨てセッションで偽ギアを登録すればBOTH化でき
  完全防御には至らない→ユニークセッション/ユーザー数での集計+レート制限+メール認証が必要
  ②questionId未検証(出題外ペアに投票可、経験フラグで実害は限定的)
  ③B3本丸=バック面1本のユーザーに質問が生成されない構造的行き止まり(最優先)

### サイクル9 対応 (①②③⑤実装済み・検証済み)
- ① 票の水増し防止: 同一セッション×ペア×軸の再回答は「最新で上書き」
  (A/B逆順の意見変更も勝者を反転して正しく上書き)。連投してもn不変を確認
- ② アカウント引き継ぎ: User.primarySessionId を追加。signup時に紐付け、
  login時にcookieを本体セッションへ付け替え+匿名データをマージ。
  旧アカウントは userId 紐付きデータからセッションを復元
  (健太: 別デバイスでギア4本・回答28件・上級プロフィール復元を確認)
- ③ パスワード認証: scrypt (Node組み込み) で User.passwordHash。
  signup必須(8文字以上)・login照合。旧アカウントは初回ログインで設定(救済)。
  gear作成時に userId も保存 (復元の手がかり強化)
- ⑤ LPコピー修正: 「両方使った人だけの比較」→「『両方使った人』に絞れる比較」
- ④ 厚さ・面別の集計絞り込み (M2) は未実装 — 次サイクル以降の最優先
- 構造的限界(コードで解決不可): 必需9にはコミュニティの実データ密度が必要。
  「ロゼナ後継に答えられない」のはデータ不足であり、偽データ投入は禁じ手

## PM仮説バックログ (ペルソナ評価と突き合わせて優先度決定)

### 大玉 (体験の根幹)

- [ ] **B1: 回答が資産にならない問題**
  10問答えても「自分に何が残るか」が見えない。マイギア間の自分の
  体感マップ (「自分はD05よりロゼナが好みだった」の一覧) を
  マイページ/ギアページに常設し、回答=自分のレビュー資産になる構造へ。
- [ ] **B2: 公称スペック数値の信頼性**
  0-100正規化した「公称値」は上級者には出所不明の数値に見える。
  メーカー間比較不能なのは業界常識。→ 数値表示をやめ相対表示にする
  / 「参考値」の出所を明示 / もしくは集計データのみに絞る判断。
- [ ] **B3: バック面文脈の弱さ**
  裏裏ドライブでもF/Bでラバー選定基準は別物。出題・switch・体感翻訳に
  面の文脈を通す (現状: ギアに面はあるが、switchは現用FH基準のみ)。
- [ ] **B4: コールドスタートの正直さ**
  n=0〜1のバーだらけだと信頼を失う。データ無し時の表示哲学を統一
  (「まだ無い」を堂々と見せ、貢献を促す)。

### 中玉

- [ ] M1: 診断のシェア画像 (動的OGP) — 流入の核
- [ ] M2: 用具ページの「同条件レビュー」絞り込み (厚さ・面)
- [ ] M3: ギア登録の摩擦低減 (人気ラバーのワンタップ候補)
- [ ] M4: battles と compare/select の役割重複の整理 (改廃候補)

### 運用

- [ ] O1: 本番スモークテスト (ネットワーク許可後)
- [ ] O2: 楽天/Amazon API での実写真・実価格 (要ユーザーのAPIキー)
